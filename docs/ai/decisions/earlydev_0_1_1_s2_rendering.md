# S2 rendering design

**Status:** MC-AI-0514 planning proposal, not implementation or qualification. Owner-confirmed requirements are a central edit-ray crosshair and fixed or two-color dark/light styling, with adaptive choice per pixel. Technical details are recommendations, not contrast or FPS guarantees. The accepted UI is integrated through [native presentation](earlydev_0_1_1_s2_presentation.md).

## Current path and ownership

`VulkanRenderer` clears and draws terrain, players, world labels and loading map into the acquired image, then opens a load-preserving GUI pass for screen glyphs. Its GUI shader emits fixed packed color and has no scene sampler; its pixel-position varying is glyph-local. See [`VulkanRenderer.hpp`](../../../src/client/include/client/render/VulkanRenderer.hpp#L225), [`text.vert`](../../../src/client/render/shaders/text.vert#L93), [`text.frag`](../../../src/client/render/shaders/text.frag#L140), and [`PresentationRenderer.cpp`](../../../src/client/render/PresentationRenderer.cpp#L3556).

Keep game decisions outside the renderer. Supply a typed per-frame HUD snapshot containing selected placement material, the shared target block/face, mode/base mode, effective rights, and pending/blocked reason. Presentation formats and submits it; it must not decide permission or reconstruct targets from rendered geometry. The interaction note owns ray rules; the world note owns edit storage, canonical cell identity and terrain-model handoff; replication owns server correction and event identity. Logical ray versus curved-surface grazing alignment remains a native acceptance question; do not claim an exact inverse ray until targeting defines one.

## Scene sampling and color

Use one renderer-owned, single-sample scene-color image per acquired swapchain image. Key its image, view, descriptor and initialized layout to the acquired image and extent; retire uses by the existing submitted-frame fences. Render the scene and depth-tested target effects into it. End that pass, transition the scene image to shader-read layout, then begin the final output pass on the acquired view: draw a full-screen composite first and the GUI afterward, in that same pass. GUI overlays sample the unchanged completed scene image, never the output being written. Use `texelFetch` at the integer framebuffer coordinate from `gl_FragCoord`, mapped for viewport origin and extent. This yields the current frame’s pixel without filtering, neighborhood averaging, previous-frame data or CPU readback.

At setup, require `VK_FORMAT_FEATURE_COLOR_ATTACHMENT_BIT | VK_FORMAT_FEATURE_SAMPLED_IMAGE_BIT` in optimal-tiling features. Query `vkGetPhysicalDeviceImageFormatProperties` for the negotiated format, optimal tiling, `VK_IMAGE_USAGE_COLOR_ATTACHMENT_BIT | VK_IMAGE_USAGE_SAMPLED_BIT`, and required extent. Create that format only; fail with a clear diagnostic if unsupported. The app owns image, memory, view and descriptors; CoreCpp retains swapchain ownership, so no API expansion is needed. Reuse scene/composite/GUI helpers offscreen with its RGBA8_UNORM output and raw-linear capture contract, while presentation captures remain sRGB encoded ([`RENDERING.md`](../../code/RENDERING.md#L55)). Recreate resources and descriptors after resize, hot reload or device recreation; reset layout state and destroy resources before their device/scope ([recreation hooks](../../../src/client/render/PresentationRenderer.cpp#L3478)). Never reuse an acquired image’s resources for another queue slot before its fence retires; allocate no scene targets per frame.

Dependency evidence is limited: the inspected CoreCpp sibling is at `618f68ce9625238039e454313b5e790ddf1350b4`, while MinecraftClone pins `5c1bad11346cfad44470f5985f1944929952b9a6`. The sibling is not proof of the pinned package’s behavior. Confirm only direct dependency assumptions against the pinned source when implementation begins; this proposal itself adds no CoreCpp API requirement.

New style colors are explicit sRGB values. For adaptive style, convert candidates and background to linear RGB: an sRGB-view fetch is already linear, encoded UNORM needs decoding, and raw-linear capture stays linear. Calculate `L = 0.2126R + 0.7152G + 0.0722B`, then choose the greater contrast ratio `(Lhigh + 0.05) / (Llow + 0.05)` using the larger/smaller candidate and scene luminances. The [W3C luminance definition](https://www.w3.org/WAI/WCAG21/Understanding/relative-luminance.html) defines linearization/luminance; its [contrast guidance](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum) gives the ratio. On equal contrast choose the configured light candidate deterministically. Apply glyph coverage alpha after color choice. Fixed style skips the contrast fetch; map-backed labels use fixed contrast against their own map/backing, rather than sampling unrelated terrain. Composite and new-style output encode once for the destination: hardware for sRGB, shader conversion for encoded UNORM, unchanged for raw-linear capture. Preserve existing `TextColor`, debug/world text and terrain semantics. This selects among configured colors; it is not a WCAG conformance claim.

Do not sample the active color attachment as an ordinary texture. Same-attachment feedback needs explicit Vulkan feedback-loop support, image usage and layout configuration, which the current path does not establish; see Khronos’ [`VK_EXT_attachment_feedback_loop_layout`](https://docs.vulkan.org/features/latest/features/proposals/VK_EXT_attachment_feedback_loop_layout.html). An app-owned sampled image keeps the ordinary dynamic-rendering path and avoids assuming that swapchain images are sampled.

## World effects and acceptance

Use shared targeting and server correction for selected block/face. Draw highlight and cracks in the scene pass with the terrain camera projection, curvature and depth. Do not use far-LOD triangles as block authority or remesh on aim changes. Cracks follow server time, clamp at completion pending acceptance, and clear on rejection/cancel; never hide a block before authoritative state changes. Spawn cubic particles only on accepted breaks, seeded by event/cell identity. Proposed presentation-only bounds: 2,048 particles, one-second lifetime, deterministic drop-oldest overflow; these are not gameplay constants.

Acceptance should capture one crosshair over alternating bright/dark pixels and verify independent choices, fixed style, glyph/alpha edges, overlap and no HUD self-sampling. Verify both capture encodings through resize and hot reload; run installed shaders on desktop and Android. Native checks cover curved/occluded targets, chunk-edge edits, server correction, crack completion/rejection and accepted-break particles. Edited holes must not retain a stale target silhouette. Measure precision/quality, memory `width × height × bytes-per-pixel × acquired-image-count`, and same-workload GPU/CPU overhead for baseline, fixed and adaptive modes. Preserve [S1 absolute performance targets](earlydev_0_1_1_s1_performance.md); make no unmeasured FPS claim.
