# S2 performance review plan

Planning only. Carry the broad S1 review into S2 as evidence to investigate, not as measured regressions or promised speedups. This plan adds no product feature or new acceptance threshold. The [S2 verification plan](earlydev_0_1_1_s2_verification.md) and [S1 carryover targets](earlydev_0_1_1_s2_delivery_targets.md) remain authoritative for their existing gates. Record later dispositions and source-bound results in the [S2 review register](earlydev_0_1_1_s2_review.md).

Inputs and source identities are retained in the [review findings](earlydev_0_1_1_s2_review_findings.json). They establish static work counts and architectural constraints, not runtime timing. Preserve current atlas, chunk, cache, queue, meshing and draw-batching designs as comparison baselines until production-path evidence supports replacement.

## Qualification boundaries

Keep the inherited moving-play predicates exact: with an identified source commit and executable/package SHA-256, a 30-second normal-launch x30 movement capture must meet at least 120 fresh FPS on Mac and 300 on Windows for at least 99% of measured moving time (completed-frame intervals at or below 1/120 s and 1/300 s, approximately 8.333 ms and 3.333 ms), with the complete 320-block Ready sphere maintained. The sphere must reach Ready within 20 seconds on Mac or 15 seconds on Windows from the original T0. Preserve raw frame IDs, timestamps, all stalls and the final tail; stationary captures and microbenchmarks cannot pass these gates.

Qualify continuous streaming separately: at x15 and x30, plus a separately labeled higher-seek run, on every required update, all 6,561 XY columns in the 40-chunk/640-block R40 set must remain current in both authoritative and submitted-visible data; any stale source or missing column fails. Record source revisions and the first deficit. R40 is distinct from the 320-block Ready sphere. Android UI, maps, input and lifecycle remain required, but no Android FPS threshold is defined here.

## Ordered evidence and work

1. **W0 — baseline and instrumentation.** On the final S1 source/package, reproduce the moving, Ready and R40 predicates before changes. Bind seed, route, settings, dependencies, hardware, source commit, package hash and raw outputs. Capture stage and end-to-end wall/CPU time, fresh-frame percentiles, update calls/s separately from fresh frames/s, capture/build/publication latency, allocations and bytes per update and published column, peak live/reserved memory, queue age/depth/wait, runnable workers and CPU time. Where hosts permit, compare 1/2/4/8/12 usable logical CPUs and distinguish affinity from worker count. Add only the instrumentation needed to expose these quantities; label unavailable GPU intervals.
2. **Resolve confirmed work.** First address **CPU-002**: callback-absent atlas preparation should skip progress snapshot creation while callback-present output stays identical. Compare cold/warm preparation on 8- and 12-logical-core hosts, including stage time, CPU time and allocation bytes. Then address **TER-01** with the W2 canonical edit state: a single edit must not make untouched profile columns scan all 1,024 blocks or allocate/retain dense arrays. Check all-height queries against `queryBlock`, collision and LOD agreement, and repeated reads plus an 18×18 capture. See [W2 world state](earlydev_0_1_1_s2_world.md).
3. **Investigate conditional capacity.** **CPU-001** does not prove oversubscription: configured workers may be idle. Compare client-only, server-only and combined local play on 8/12 logical cores, with explicit worker counts and a bounded shared-budget candidate; report remote-server load separately. Change pool sizing only if queue delay, runnable work and frame/publication tails identify contention. **CPU-003** is also conditional: measure update calls, successful captures, deadline exits, current/presented R40 sets and stale-scene age on cardinal, diagonal, turns, reversals, wraps and higher-seek routes. Change the per-update cap or cancellation policy only when that evidence identifies it as the limiter.
4. **Run targeted alternatives only after W0.** Measure allocation and layout changes on the same production traces, including reusable frontier sets, retained capture buffers, bounded scene scratch and image caching one at a time. Compare current hash table/hasher, a flat table with the same hasher, and alternate hashers separately, using recorded real coordinate/session/token/string keys, hit/miss mix, churn and reference-stability needs; include full-operation cost, allocations, memory and collision spread. For SIMD, compare scalar/reference and compiler-optimized code before one independent lane at a time; inspect vectorizer diagnostics/disassembly, preserve fixture identity and exact numerical results, and do not use global fast-math. Keep current CPU culling as baseline; prototype GPU culling only if profiling warrants it.
5. **Qualify rendering cost.** **GPU-01** requires whole-frame or relevant scene/composite/map/GUI timing tied to the acquired slot and retired fence. Compare the same scene, device, extent and camera for baseline, fixed HUD, adaptive HUD and maps. Report CPU and GPU p50/p95/p99, target memory and unsupported-path reasons. On MoltenVK, use a trustworthy platform trace or mark GPU timing unavailable; do not call pass timing utilization. Coordinate affected work with [W5 interaction/UI](earlydev_0_1_1_s2_ui.md), [W6 rendering](earlydev_0_1_1_s2_rendering.md) and [W7 map pipeline](earlydev_0_1_1_s2_map_pipeline.md).

Accept a change only with matched, repeatable production-path evidence, preserved S1 correctness/numerical identities, and no regression in the applicable gates. Keep current implementations when results are inconclusive; no target requires using every logical core or adopting SIMD, flat hashing or GPU work.
